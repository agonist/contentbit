`contentbit.config.*` is the shared project interface used by `check`,
validation, Studio, links, briefs, generated instructions, and agent guidance.

```ts
import { defineContentConfig } from '@contentbit/core'

export default defineContentConfig({
  content: 'content/**/*.{md,mdx}',
  registry: './blocks/registry.ts',
  genericBlocks: true,
  links: {
    resolve: 'same-locale-key',
    localeField: 'locale',
    keyField: 'key',
    slugField: 'slug',
    defaultLocale: 'en',
  },
  seo: './contentbit.seo.config.ts',
  site: {
    build: 'dist',
    origin: 'https://example.com',
  },
})
```

## File discovery

Contentbit walks upward from the current directory and uses the nearest
`contentbit.config.ts`, `.mts`, `.mjs`, or `.js`. The search stops at the
nearest `package.json`, which lets each package in a monorepo own its content
boundary. Paths and globs in the config are resolved relative to the
configuration file, not the shell's current directory.

## Top-level fields

| Field | Type | Default | Meaning |
| --- | --- | --- | --- |
| `content` | `string \| string[]` | None | One or more Markdown or MDX files/globs. `defineContentConfig` normalizes a string to an array. A site without Markdown can leave it out. |
| `registry` | `string` | None | Module that default-exports custom block definitions. |
| `genericBlocks` | `boolean` | `true` | Include the built-in generic block pack before the custom registry. |
| `links` | `LinkResolverOptions` | Global slug resolution | Shared page identity and locale fields for the internal-link graph. |
| `seo` | `string \| false` | Automatic SEO config discovery | Path to an SEO contract module, or `false` to disable discovery. |
| `site` | `ContentbitSiteConfig` | None | The build folder and public origin that `contentbit check` reads. See [Site fields](#site-fields). |

Commands that read Markdown, such as `validate`, `links`, and `studio`, need
`content` or explicit globs. `contentbit check` reads Markdown only from
`content`, and checks the built pages without it.

## Site fields

| Field | Type | Default | Meaning |
| --- | --- | --- | --- |
| `build` | `string` | The first of `dist/client`, `dist`, `out`, `build`, and `public` that has an `index.html` | The static build folder, relative to the config file. |
| `origin` | `string` | The origin most canonical URLs use | The site's public origin, such as `https://example.com`. It must be an absolute `http` or `https` URL. Only its origin is kept. |
| `draftField` | `string` | `draft` | Frontmatter field that marks a document as a draft when it is `true`. |
| `dateField` | `string` | `date` | Frontmatter field with a document's publication date. |

`check` neither expects a built page for a draft or a document dated after
today, nor compares one with its source document.

## Link resolver fields

| Field | Type | Default | Meaning |
| --- | --- | --- | --- |
| `resolve` | `global-slug \| same-locale-slug \| same-locale-key \| prefer-same-locale-key-fallback-slug` | `global-slug` | How a `linksTo` target identifies a page. |
| `localeField` | `string` | `locale` | Frontmatter field containing the page locale. |
| `slugField` | `string` | `slug` | Frontmatter field containing the public slug. |
| `keyField` | `string` | `key` | Frontmatter field containing stable translation identity. |
| `defaultLocale` | `string` | None | Locale assigned when a participating page omits its locale field. |
| `routes` | `Record<string, string>` | None | Public URL pattern for the content files under each directory. See [Page routes](#page-routes). |
| `hostRoutes` | `string[]` | None | Routes the host app serves outside the scanned content, such as `/playground`. |

Use `same-locale-slug` when translated pages have distinct identities but may
reuse a slug. Use `same-locale-key` when translations share a stable key. Use
the fallback mode when key-based links are preferred but legacy slug targets
must continue to resolve.

## Page routes

`routes` gives each Markdown document the URL of its built page, and
`hostRoutes` lists the paths the host app serves outside the content.
`contentbit check` uses them to:

- point a built-page finding at the line of the source document that wrote it,
- compare each page's title and meta description with the document's
  frontmatter,
- report a published document whose route has no built page, and
- accept a link to a host route that the build folder does not contain.

Describe the routes your host app serves, for example by file path:

```ts
export default defineContentConfig({
  content: 'content/**/*.{md,mdx}',
  links: {
    routes: {
      'content/docs': '/docs/{path}',
      'content/blog': '/blog/{slug}',
    },
    hostRoutes: ['/pricing', '/playground'],
  },
})
```

Each key is a directory relative to the config file. A page takes its URL from
the deepest directory that holds it. Patterns can use these placeholders:

| Placeholder | Value |
| --- | --- |
| `{path}` | The file path below the directory, without `.md` or `.mdx` and without a final `index`, so `content/docs/guides/index.mdx` gives `guides`. |
| `{slug}` | The page's slug, read through `slugField`. |
| `{key}` | The page's key, read through `keyField`. |
| `{locale}` | The page's locale, read through `localeField`, or `defaultLocale`. |

A page outside every route directory, or one missing a fact its pattern needs,
has no URL. A route and a `hostRoutes` entry match a built page path while
ignoring a trailing slash. `hostRoutes` entries are exact routes, and they
apply with or without `routes`.

Links in Markdown to internal URLs and `#anchor`s are checked on the built
pages, where the rendered ids and URLs are known. The Markdown checks still
report a relative `.md` or `.mdx` link to a file that does not exist.

## Command overrides

Explicit files, globs, `--registry`, `--seo-config`, link-field flags, and
`--no-generic-blocks` override the discovered config for one invocation.
Relative paths you pass on the command line resolve against the shell's current
directory. Commands that accept `--no-seo` can disable the configured SEO
contract for one run.

When no config exists, project-aware commands can reuse a matching script from
the nearest `package.json` for backward compatibility. Once a config exists,
config discovery wins over package-script inference.

For the setup procedure, see [Configure a Contentbit project](/docs/guides/project-config).
For every command option, see the [CLI reference](/docs/reference/cli).
