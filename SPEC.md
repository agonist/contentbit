# Content Blocks Spec

Status: draft, incubated from the `apps/landing-beta` content block system on 2026-06-10.

Name: Content Blocks, shipped under the contentbit brand (CLI `contentbit`, npm scope `@contentbit`, site contentbit.dev). Scope renamed 2026-06-10.

## Thesis

Content Blocks is a framework-agnostic component block layer for Markdown.

It lets teams write generated, localized, CMS-managed, or human-authored Markdown with
structured component blocks, validate that content against explicit schemas, and render
the same content through different adapters such as React, static HTML, Astro, Vue,
Svelte, email-safe HTML, or plain Markdown fallback.

The React/shadcn integration is the first distribution target, not the whole product.
The durable asset is the content protocol.

## One-line Positioning

Structured Markdown components without framework lock-in.

## Why This Exists

`apps/landing-beta` already has a useful internal pattern:

- authors and LLMs write Markdown with custom blocks like `:::tabs`, `:::steps`,
  `:::comparison`, and `:::recipe-card`
- a registry documents when each block should and should not be used
- the renderer turns blocks into visually richer article components
- only interactive blocks need hydration

That pattern is worth extracting, but the open source version should be more generic
and more formally designed:

- parse to a block AST, not directly to raw HTML
- validate content with line-level diagnostics
- keep schemas, examples, and authoring guidance beside each block definition
- support multiple render targets
- let users add custom blocks easily
- ship default shadcn-compatible components through a shadcn registry

## Why Not MDX

MDX is excellent when trusted developers want arbitrary JSX inside content.

Content Blocks solves a different problem:

- content may be generated by LLMs
- content may be localized or edited in a CMS
- content should remain Markdown-shaped and portable
- authors should not need React or JSX knowledge
- teams want validation before render
- teams want renderer choice instead of React lock-in

MDX embeds components. Content Blocks defines a content protocol.

Use MDX when:

- authors are developers
- content lives close to app code
- arbitrary React power is desired
- build-time JSX execution is acceptable

Use Content Blocks when:

- content is generated, imported, translated, or CMS-managed
- strict block schemas matter
- line-level content errors are valuable
- content should render outside React
- LLMs or skills need clear authoring instructions

The system can be MDX-compatible later by providing an MDX plugin or renderer, but it
should not depend on MDX as the primary model.

## Product Goals

V1 should deliver:

- a small directive-style Markdown block syntax
- a core parser that produces a source-mapped AST
- a registry API for built-in and custom blocks
- validation with useful diagnostics
- authoring instruction generation for LLMs, skills, and docs
- a default generic block pack
- a React renderer
- a static HTML renderer
- shadcn registry distribution for React components, hooks, and utilities
- a CLI for validating content and exporting instructions

The project should feel useful even if a user never installs the shadcn components.

## Non-goals

V1 should not attempt to be:

- a full Markdown parser replacement
- a CMS
- an MDX clone
- a visual page builder
- a general component runtime
- a layout system for arbitrary app UI
- a block editor
- a proprietary content format

The system is for structured editorial/content blocks inside Markdown.

## Design Principles

### Markdown stays readable

A document should remain understandable in a plain text editor. Blocks can add
structure, but they should not turn prose into unreadable config.

### Schemas are first-class

Every block defines:

- name
- props schema
- content schema
- allowed children
- examples
- authoring guidance
- render capability

The registry is not only a renderer map. It is the source of truth for content
contracts.

### Validation before rendering

Invalid content should produce diagnostics with source positions before rendering.
Renderers may choose to degrade gracefully, but validation should be explicit.

### Frameworks are adapters

The parser and registry should not know about React, Astro, Vue, or Svelte. Renderers
consume a validated AST.

### Default components are replaceable

The built-in visual pack is a starting point. Users should be able to replace any
renderer for any block without changing content.

### LLM guidance is generated from the registry

The same block definitions that validate content should produce instructions for
content generation tools. This keeps examples, usage rules, and schemas from drifting.

## System Overview

```text
content.md
  -> parse
  -> block AST with source positions
  -> validate against registry
  -> render adapter
  -> React / HTML / Astro / Vue / Svelte / Markdown fallback
```

The core package owns parsing, AST types, validation, registries, diagnostics, and
instruction generation.

Renderer packages own output-specific behavior.

Distribution packages own installable component code.

## Terminology

### Document

A Markdown file or string that may contain normal Markdown and Content Blocks.

### Block

A structured content component expressed using directive syntax.

Example:

```md
:::comparison{left="Basic" right="Pro"}
- Price | Free | $12/mo
- Support | Community | Priority
:::
```

### Child block

A nested block that is only meaningful inside a parent block.

Example:

```md
:::tabs
::tab{title="Fast"}
Use this when time matters.
::tab{title="Cheap"}
Use this when budget matters.
:::
```

### Block definition

The registry object that defines how a block parses, validates, renders, and explains
itself to authors.

### Registry

A collection of block definitions. Registries can be composed from built-in packs and
user-defined blocks.

### Diagnostic

A parser or validation message with severity, source position, block name, and a fix
hint when possible.

## Content Syntax

### Block open and close

Blocks use fenced directive syntax:

```md
:::block-name{prop="value" count=3 enabled=true}
Block body
:::
```

Rules:

- block names use lowercase kebab-case
- props are optional
- a block closes with `:::` on its own trimmed line
- nested blocks are allowed only when the parent block definition permits them
- unknown blocks are diagnostics, not silently ignored
- block delimiters inside fenced code blocks (``` or `~~~`) are literal text, never
  parsed as blocks
- when three-colon blocks nest, a closing `:::` matches the innermost open block; an
  outer block may use a longer fence (`::::`) to disambiguate, mirroring
  `remark-directive` conventions

### Child block open

Child blocks may use two-colon syntax:

```md
::item{title="First"}
Body
```

Child block close rules are parent-specific. For V1, a child block body ends at the
next sibling child block or the parent close. Three-colon blocks nested inside a child
body must be balanced before the child ends.

Note: `::name` is a *leaf* directive (no body) in `remark-directive`. Giving child
blocks bodies is a deliberate divergence and must be documented as such.

### Props

V1 supports a constrained prop grammar:

```md
{title="Quick Reference" count=3 variant="compact" featured=true}
```

Supported values:

- quoted strings
- numbers
- booleans
- bare identifiers for enums, if the block schema allows them

Unsupported in V1:

- JavaScript expressions
- object literals
- arrays
- function references
- JSX

This is intentional. The syntax should be safe for generated content and portable
across renderers.

### Row bodies

Many generic blocks can use pipe rows:

```md
:::key-metrics
- 42% | Conversion lift
- 18ms | Median parse time
:::
```

Rows are parsed by the block definition, not by the global parser. This lets each
block define the number of columns, labels, and error messages.

A literal `|` inside a cell is escaped as `\|`.

### Markdown bodies

Blocks may allow Markdown content:

```md
:::callout{type="tip" title="Worth knowing"}
You can use **Markdown** inside this block.
:::
```

The core parser should preserve body ranges. Renderers can pass Markdown fragments
through the host Markdown pipeline or a package-provided Markdown renderer.

### Raw HTML

Raw HTML should be disabled by default in Content Blocks parsing and rendering.

If a project needs raw HTML, it should opt in at the renderer level and own
sanitization.

## AST

The parser should produce an AST that preserves normal Markdown segments and block
nodes.

Sketch:

```ts
type DocumentNode = {
  type: "document"
  children: ContentNode[]
  position: SourceRange
}

type ContentNode = MarkdownNode | BlockNode

type MarkdownNode = {
  type: "markdown"
  value: string
  position: SourceRange
}

type BlockNode = {
  type: "block"
  name: string
  props: Record<string, unknown>
  rawProps: string | null
  children: ContentNode[]
  body: string
  position: SourceRange
  openPosition: SourceRange
  closePosition: SourceRange | null
}

type SourceRange = {
  start: SourcePoint
  end: SourcePoint
}

type SourcePoint = {
  line: number
  column: number
  offset: number
}
```

Validated block nodes can attach parsed, block-specific data:

```ts
type ValidatedBlockNode<TData = unknown> = BlockNode & {
  data: TData
  definition: BlockDefinition<TData>
}
```

## Parser Requirements

The parser should:

- be deterministic
- be source-mapped
- preserve Markdown text exactly where possible
- support nested block parsing
- recover from errors enough to report multiple diagnostics
- treat fenced code blocks as opaque: `:::` inside a code fence is never a delimiter
- avoid executing code
- avoid output-specific decisions

The parser should not:

- emit HTML
- know about React components
- rely on regex-only global replacement
- silently repair malformed blocks without diagnostics

## Validation

Validation happens after parsing and before rendering.

Validation checks:

- block exists in registry
- props match schema
- body shape matches block content model
- children are allowed
- required child blocks are present
- row counts and column counts match expectations
- enum values are valid
- links and URLs follow security policy
- nesting depth is within configured limits

Diagnostic shape:

```ts
type Diagnostic = {
  code: string
  severity: "error" | "warning" | "info"
  message: string
  hint?: string
  blockName?: string
  position: SourceRange
}
```

Example diagnostic:

```text
content.md:12:3 error CB_COMPARISON_ROW_COLUMNS
comparison rows require 3 columns: Label | Left value | Right value.
Found 2 columns.
```

## Block Definition API

The registry API should make custom blocks easy without hiding the important parts.

Sketch:

```ts
const comparisonBlock = defineBlock({
  name: "comparison",
  description: "Side-by-side comparison for exactly two options.",
  props: z.object({
    left: z.string().min(1),
    right: z.string().min(1),
  }),
  content: pipeRows({
    columns: ["label", "left", "right"],
    minRows: 2,
    maxRows: 12,
  }),
  authoring: {
    useWhen: [
      "Comparing exactly two things across multiple attributes",
      "Replacing a two-column Markdown table",
    ],
    avoidWhen: [
      "Comparing more than two things",
      "The comparison only has one row",
    ],
    example: `:::comparison{left="Option A" right="Option B"}
- Speed | Fast | Slow
- Setup | Simple | Advanced
:::`,
  },
})
```

Block definitions are renderer-agnostic. Each adapter maps block names to its own
implementations, so core never references framework code:

```ts
// @contentbit/react
const components = { comparison: ComparisonBlock }

// @contentbit/html
const htmlRenderers = { comparison: renderComparisonHtml }
```

Custom block example:

```ts
registry.add(
  defineBlock({
    name: "pricing-table",
    description: "Compares product plans.",
    props: z.object({
      currency: z.enum(["usd", "eur", "gbp"]).default("usd"),
    }),
    content: pipeRows({
      columns: ["plan", "price", "features"],
      minRows: 2,
    }),
    authoring: {
      useWhen: ["Comparing SaaS pricing plans"],
      avoidWhen: ["Listing non-pricing feature differences"],
      example: `:::pricing-table{currency="usd"}
- Starter | $0 | Basic usage
- Pro | $12/mo | Teams and automation
:::`,
    },
  }),
)
```

## Content Model Helpers

Most users should not need to write custom parsers for common body shapes. The core
package should provide helpers that cover the default blocks and most project-defined
blocks.

Proposed helpers:

```ts
markdownBody({
  minLength?: number
  maxLength?: number
})

pipeRows({
  columns: string[]
  minRows?: number
  maxRows?: number
  allowMarkdown?: boolean
})

listItems({
  marker: "bullet" | "ordered" | "signed" // signed = `+` / `-` lines (e.g. pros-cons)
  minItems?: number
  maxItems?: number
})

children({
  allowed: string[]
  required?: string[]
  minChildren?: number
  maxChildren?: number
})
```

The helper output should include parsed `data` and diagnostics. For example,
`pipeRows` should return rows keyed by column name:

```ts
type ComparisonData = {
  rows: Array<{
    label: string
    left: string
    right: string
  }>
}
```

Complex blocks can still provide a custom `parseContent` function.

## Public API Sketch

The smallest useful API should look roughly like this:

```ts
import {
  createBlockRegistry,
  parseDocument,
  validateDocument,
} from "@contentbit/core"
import { genericBlocks } from "@contentbit/blocks-generic"
import { renderToHtml } from "@contentbit/html"

const registry = createBlockRegistry().use(genericBlocks())

const ast = parseDocument(markdown)
const result = validateDocument(ast, registry)

if (!result.ok) {
  console.error(result.diagnostics)
}

const html = renderToHtml(result.document, { registry })
```

React usage:

```tsx
import { ContentBlocks } from "@contentbit/react"

export function Article({ document }: { document: ValidatedDocument }) {
  return <ContentBlocks document={document} components={components} />
}
```

Project extension:

```ts
const registry = createBlockRegistry()
  .use(genericBlocks())
  .add(pricingTableBlock)
```

## Registry

The registry should support:

- built-in block packs
- project-level custom blocks
- namespacing to avoid collisions
- reading authoring metadata
- exporting docs and prompts
- validating one document or many documents

Renderer replacement happens at the adapter level (e.g. the `components` prop of the
React renderer), not in the registry. The registry owns content contracts only.

Sketch:

```ts
const registry = createBlockRegistry()
  .use(genericEditorialBlocks())
  .add(pricingTableBlock)
```

Collision policy:

- duplicate names error by default
- `override` must be explicit
- namespaced blocks use `namespace:block-name` in code, but should expose a
  Markdown-safe alias when possible

Versioning:

- block definitions should include a semantic version
- validation should know the block version used by a document when available
- breaking syntax changes require a new block version or migration

## Authoring Instructions

Each block definition should generate machine-readable and human-readable
instructions.

Instruction outputs:

- Markdown docs
- compact LLM prompt context
- Codex skill snippets
- validation schema summaries
- example catalogs
- `llms.txt`-style content guidance

Sketch:

```ts
registry.toAuthoringGuide({
  audience: "llm",
  includeExamples: true,
  includeAvoidRules: true,
  maxTokens: 2000,
})
```

Guidance should include:

- allowed block names
- exact syntax
- when to use each block
- when not to use each block
- minimum and maximum recommended content
- examples
- common validation failures

This is a core differentiator. Content generation should not depend on stale manual
prompt snippets.

## Skills Integration

The package should make it easy to create agent skills that generate valid content.

Potential outputs:

- `skills/content-blocks/SKILL.md`
- `skills/content-blocks/references/blocks.md`
- `skills/content-blocks/scripts/validate-content.ts`

Skill instructions should tell agents:

- write regular Markdown by default
- use blocks only when they improve scanning or structure
- never invent block names
- follow the block examples exactly
- run validation before finalizing generated content
- fix diagnostics rather than bypass them

The generated skill should be derived from the registry so teams can include their
custom blocks.

## Renderers

### Static HTML renderer

The HTML renderer should:

- render validated blocks to HTML strings
- sanitize links and user content
- support optional class name prefixes
- support plain Markdown fallback for unsupported blocks
- avoid hydration assumptions

### React renderer

The React renderer should:

- map validated blocks to React components
- accept component overrides
- support server rendering
- keep interactive behavior opt-in per block
- expose hooks or helpers for hydration only where needed

### Markdown fallback renderer

The Markdown fallback renderer should:

- convert blocks into readable plain Markdown
- be useful for email, exports, search indexing, or unsupported environments
- preserve the information even if visuals are lost

### Future adapters

Potential later adapters:

- Astro components
- Vue components
- Svelte components
- MDX transform
- email-safe HTML
- PDF/docx export

## shadcn Distribution

The default React component pack should be distributed through a shadcn registry.

Relevant current shadcn registry facts:

- a registry can distribute custom components, hooks, pages, config, rules, and
  other files
- the registry system is not limited to React
- a registry exposes a root `registry.json` catalog
- individual items are served as item JSON files
- item types include `registry:block`, `registry:component`, `registry:hook`,
  `registry:lib`, `registry:file`, and others
- users can install from direct item URLs or add a namespace such as
  `@contentbit=https://example.com/r/{name}.json`

Sources checked on 2026-06-10:

- https://ui.shadcn.com/docs/registry
- https://ui.shadcn.com/docs/registry/getting-started
- https://ui.shadcn.com/docs/registry/registry-item-json

Install flow example:

```bash
pnpm dlx shadcn@latest registry add @blocks=https://contentbit.dev/r/{name}.json
pnpm dlx shadcn@latest add @blocks/comparison
pnpm dlx shadcn@latest add @blocks/content-renderer
```

Registry items should be organized so users can install:

- one block at a time
- the complete generic pack
- renderer utilities
- hooks for interactive blocks
- authoring/validation helper files

Example shadcn item grouping:

```text
@blocks/content-renderer
@blocks/callout
@blocks/comparison
@blocks/key-metrics
@blocks/tabs
@blocks/troubleshoot
@blocks/generic-pack
```

The registry should install editable source files into the user's app. Users own the
visual implementation after install.

## Default Generic Block Pack

V1 should ship blocks that work across many niches.

### Foundation blocks

- `callout`: note, tip, warning, important, TLDR
- `steps`: ordered process steps
- `checklist`: actionable checklist
- `summary-box`: short takeaways
- `quick-ref`: compact key/value reference
- `key-metrics`: scannable metrics/stat cards

### Comparison and decision blocks

- `comparison`: exactly two options
- `pros-cons`: paired advantages and disadvantages
- `decision-matrix`: multiple options across criteria
- `spec-table`: structured facts/specifications

### Interaction blocks

- `tabs`: alternate methods, variants, or audiences
- `accordion`: expandable sections
- `faq`: question/answer pairs
- `troubleshoot`: symptom/cause/fix items

### Time and process blocks

- `timeline`: chronological milestones
- `schedule`: time-boxed agenda

### Media and proof blocks

- `figure`: image with caption and attribution
- `quote-card`: testimonial or expert quote
- `resource-list`: curated links with descriptions

V1 should avoid niche-first blocks such as `recipe-card` in the default pack. Those can
ship as examples or future vertical packs.

Potential vertical packs:

- recipes and cooking
- SaaS marketing
- product docs
- education
- travel
- finance
- fitness

Possible monorepo package layout:

```text
packages/
  core/              # parser, AST, registry, validation, diagnostics
  markdown/          # Markdown integration helpers
  html/              # static HTML renderer
  react/             # React renderer primitives
  shadcn/            # source files for shadcn registry
  cli/               # validate, docs, instructions, registry build helpers
  skills/            # generated/default skill templates
  blocks-generic/    # default generic definitions
  blocks-recipes/    # optional vertical pack
```

Open question: whether generic block definitions live in `core` or in
`blocks-generic`. Prefer `blocks-generic` so `core` stays small.

## CLI

The CLI should support:

```bash
contentbit validate content/**/*.md
contentbit render content/article.md --target html
contentbit instructions --target llm --out content-blocks.md
contentbit docs --out docs/blocks.md
contentbit init
contentbit registry build
```

Later:

```bash
contentbit repair content/article.md
contentbit migrate content/**/*.md --from 1 --to 2
```

The repair command should not be in V1 unless it is simple and safe.

## Security

Security defaults:

- no JavaScript expressions in content
- no arbitrary JSX
- raw HTML disabled unless explicitly enabled
- URLs validated by protocol
- renderer output escaped by default
- interactive components receive data only, not executable code
- max nesting depth configurable
- max block size configurable

Allowed URL protocols by default:

- `http:`
- `https:`
- `mailto:`

Everything else requires opt-in.

## Accessibility

Default components should meet baseline accessibility requirements:

- tabs use proper tablist/tab/tab-panel semantics
- accordions and troubleshoot blocks use buttons, not clickable divs
- interactive state is keyboard accessible
- focus states are visible
- color is not the only state signal
- generated IDs are stable
- headings and labels remain meaningful in fallback renderers
- motion is minimal and respects reduced motion preferences

Accessibility metadata can be included in block definitions when useful.

## Styling

The core package should not ship a visual theme.

The shadcn pack should:

- use Tailwind classes compatible with shadcn projects
- use `cn` helper conventions
- compose existing shadcn primitives where appropriate
- keep components easy to edit after install
- avoid hard-coded brand colors where possible
- expose variant props only when they are content-level choices

Renderer-level class prefixing should be supported for static HTML users.

## Localization

Lessons from `landing-beta`, where troubleshoot badge labels were hard-coded per
language in the pipeline:

- block definitions and core never contain display strings
- content-level text lives in the document or block props; documents in different
  languages share the same block names and props
- renderer-level chrome labels (e.g. "Do" / "Don't", tab list aria-labels) come from a
  `labels` option on the renderer, with English defaults
- fallback renderers use the same labels option so exports stay localized

## Error Handling and Fallbacks

Renderers should support three modes:

- `strict`: throw on validation errors
- `annotated`: render visible developer diagnostics
- `fallback`: render invalid blocks as escaped plain Markdown with comments

Recommended defaults:

- development: `annotated`
- CI: `strict`
- production: `fallback` if content is user/CMS supplied, `strict` if content is
  repository-owned

## Success Criteria

The library is successful when:

- a user can define a custom block in under 20 lines of code
- generated content can be validated with useful line-level errors
- the same content renders through React and static HTML
- the default shadcn components can be installed and customized
- an LLM can use the generated authoring guide without inventing invalid blocks
- an existing Markdown document remains readable without the renderer

## Open Questions

- Should the directive syntax exactly follow `remark-directive` conventions? Two known
  divergences already exist: child blocks have bodies (leaf directives do not), and
  the attribute grammar is simpler than directive attributes (`{#id .class}` is not
  supported). Decide whether to document these as deliberate or converge.
- Should unknown blocks be errors or warnings by default?
- Should inline directives (`:name[text]{props}`) ever be supported, or container
  blocks only? (Lean: container-only, list inline as a non-goal.)
- Should renderers support streaming partial documents, so LLM-generated content can
  render progressively while it arrives? This could be a real differentiator for AI
  products and affects parser design (incremental, error-tolerant parsing).
- How much Markdown parsing should core own versus delegating to unified/remark?
- Should block versions be encoded in content or only in registry/config?
- Should the first docs site be inside this repo or in a new OSS repo?
- Should the shadcn pack depend on Radix primitives directly or compose installed
  shadcn primitives?
- Should vertical packs live in the same registry namespace?
